状态：待设计、待实施。后续接入渠道包括企业微信、小程序或公众号，具体选型与接入顺序待定；先建设可供不同入口共用的账号和权限基础。

- [ ] 建立权限关系：用户关联组织、角色和可管理的数据范围；支持用户兼任多个角色，并关联负责的园区、区域或承租方。建议初始角色包括管理员、财务、运营、维修人员、承租方及只读查看者，最终权限矩阵在实施时确认。
- [ ] 区分操作权限与数据权限：分别控制查看、录入、修改、导出、收款登记、账单调整、管线维护、工单处理和账号管理；支持全园区、指定区域、本人承租区域、分派工单等数据范围。承租方只能查看获授权的自身房间和账单，维修人员只获得履行工单所需的资料。
- [ ] 权限在服务端统一校验：页面、接口和导出使用同一套授权规则，默认不授予未配置的权限；为不同角色提供对应页面入口和可执行操作。替换当前整份园区数据统一返回与覆盖的接口，避免受限用户获取全园数据或修改无权访问的记录。
- [ ] 账号与授权生命周期：支持邀请、绑定、停用、角色调整和数据范围调整；员工离职、承租关系结束或权限撤销后，既有会话和访问权限及时失效。记录授权变更、账单调整、收款登记等关键操作的经办人、时间和变更内容。
- [ ] 预留企业微信接入：围绕内部员工身份关联、业务入口、待办及工单通知设计；接入前核对实际企业配置和所需平台能力。
- [ ] 预留小程序或公众号接入：围绕承租方身份绑定、本人账单与用量查询、报修及进度查询、消息通知设计。具体平台能力、认证及消息授权要求在选型时核实；在线支付如需接入，另立待办定义，不默认包含在本项中。
- [ ] 统一内部身份：以内部用户ID为主体，将不同平台身份按所属企业或应用分别绑定；外部身份登录成功后仍需校验内部账号状态、角色与数据范围，不因登录渠道自动提升权限。支持经核验的绑定、解绑与账号关联，避免同一人在不同入口产生互不关联的数据。
- [ ] 统一业务接口与通知机制：网页、企业微信、小程序和公众号共用账单、工单及权限规则；通知只发送至获授权的接收人，预留渠道开关、发送记录、失败重试和去重。平台密钥、回调校验与凭据更新在服务端管理。

验收场景：两个承租方互相无法读取账单；维修人员可以更新授权管段或工单但不能修改收款；账号停用后所有入口失去访问权限；同一用户经核验绑定不同入口后看到一致的数据；越权调用接口及导出均被拒绝。

## 界面与使用流程

主界面应围绕“哪个房间需要我处理什么”组织：园区图负责定位，右侧展示房间概况及四类费用，电表放在电费下面。进一步优化：

1. 右侧费用卡统一显示账期、应收、已收、待收与状态；年付房租突出覆盖区间，不让用户误认为每月都要交全年租金。
2. “记收款”改为填写**本次收到多少**并预填待收，自动形成流水；用户不必理解或手算累计实收。
3. 自动费用展示“本期用量×单价”和抄表时间；异常时明确停算原因，不能用0冒充未知。
4. 历史记录在每个费用项目内直接展开，兼有统一账单列表；保留费用筛选和年份选择。
5. 首页优先展示待收、即将到期、设备过期未抄等可操作事项；手机上将地图和详情拆成可切换视图。
6. 本地/服务器模式、保存状态、加载失败的文案统一；读数记录中的“本机”旧文案仍可进一步调整。

## 工程与运维

- 目前SQLite中按JSON存整个园区，适合小规模试运行；正式多人使用需拆分设备、房间、合同、账单、收款等实体并使用数据库约束，避免全量上传和重复扫描。
- 金额与电量的数值精度、换表/回退、改价、跨月、部分收款、退款等需要专项自动化测试，现有20项并非完整业务验收。
- 前端运营页较大，需拆分收费、历史、招标及地图状态；建立UI组件规范与移动端回归用例。
- 供应商接口当前使用HTTP并在请求参数携带授权码；需与供应商确认受支持的HTTPS地址/证书，不能用跳过证书校验替代。配置已放服务端，但链路本身尚未加密。
- 已有同机每日备份与100个版本快照；还缺异地备份、定期恢复演练、备份容量及失败告警。
- IP短期证书需要可靠续期；已启用定时器，仍应增加到期和续期失败告警。业务连续性需要发布目录、回滚和健康检查。
- 框架为vinext beta，Node内置SQLite仍显示实验性提示；应建立依赖锁定、安全更新和升级回归流程。
- 现有服务器还有其他服务，含公开监听的MySQL和面板端口。本次没有变更这些服务；需单独核对是否需要公网访问并收紧来源。

推荐实施顺序：**后台采集与结算 → 全费用收款流水 → 合同与收费规则 → 正式权限和审计 → 报表、移动端及运营体验**。各阶段以具体业务场景验收，逐步替换演示数据。
